# History

This addon's reasoning is almost all current and lives in [document.md](document.md) and [integration.md](integration.md). The failures worth recognising:

- **The whole server was one capsule.** Every game drew stock characters by hashing an id and preferred what the platform resolved, and the platform resolved `schema.default_avatar()` for everybody with nothing stored. The variety lasted until dot-platform admitted somebody. Fixed by `default_avatar_fn` ([integration](integration.md#a-player-with-nothing-stored-is-the-games-default-when-it-has-one)).
- **Every member arrived as stock in every game.** The site's avatar is over its own `builtin` schema, and `conform` refuses another schema's document. Fixed by `translate_fn` ([integration](integration.md#the-sites-avatar-is-over-the-sites-schema-and-a-game-translates-it)).
- **Every member who never opened the site's editor translated to the same person**, because the site answers with a default document for them. Fixed by treating `saved: false` as no avatar.
- **The trap tinting avoids:** editing a part's material in place recolours everyone wearing that part, because they share the loaded `Resource`. Only visible with two players in the level; tints are per-instance shader parameters.
- **No site avatar ever reached a game (found 2026-10-11).** `DotAvatarStoreBackbone` built its `DotHttp` and never put it in the tree, so every read failed with engine error 3 (Unconfigured) before a packet left the process, and `DotAvatarManager.resolve` answered each with a WARN ("could not read an avatar; using the default") and the game's stock look: exactly what a member with nothing saved sees, so it looked like nobody had saved one. The suite drove the store only through `FakeBackboneHttp`, which overrode `request()` and so never needed the tree. Found because dot-user's `DotUserStoreBackbone` had the identical bug. Fixed by parenting the client on `open` and freeing it on `close`; the fake now refuses outside the tree and a section drives the real client ([integration](integration.md#the-backbone-store-and-why-the-wire-format-is-not-the-packed-one)).
- **The digest disagreed with the site's for the site's own slots (found the same day).** `filled_slots()` used `sort()`, which orders StringNames by interning, so `face`/`top`/`legs` hashed as `legs, face, top` while the site sorted by text. The site's fixtures (`hair`, `top`) happened to intern in alphabetical order and every other check compared Godot with Godot, so nothing failed; with the store fixed, every client would have re-fetched every avatar on every join. Fixed with a text `sort_custom` and a section pinned to the site's values ([document](document.md#the-digest-and-why-a-profile-carries-it)).
- **Two overlapping opens queued one client twice.** With `_open` now suspending a frame, the manager's `_ready` and dot-platform's explicit `setup()` both opened the store, and the second `add_child` was an engine error on every server boot. `DotAvatarStore.open()` now shares one in-flight attempt.
